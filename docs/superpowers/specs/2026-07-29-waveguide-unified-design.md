# 도파관 통합 비교 시뮬레이션 — 통합 설계 v1.1

> 기준 문서: `waveguide_unified_spec_v1.md` (이하 **v1**)
> 이 문서는 v1을 대체하지 않는다. **v1을 읽은 뒤 이 문서를 읽는다.**
> v1과 충돌하는 항목은 §1 표에 전부 모아 두었고, 그 항목은 **이 문서가 우선**한다.
> 작성일: 2026-07-29

## 0. 이 문서가 만들어진 이유

v1을 원본 코드 7개 파일과 대조한 결과, 두 종류의 문제가 나왔다.

**(가) 사실 오류** — v1이 "원본이 이미 이렇게 한다"고 적었으나 원본이 그렇게 하지 않는 곳.
**(나) 자기모순** — v1이 §8에서 스스로 경계한 실수를 v1의 다른 절이 저지르는 곳.

두 종류 모두 조용히 넘어가면 "그럴듯한 숫자"를 만들어 내므로, 확정해서 이 문서에 남긴다.

## 2. 저장소 (§2 보완)

v1 §2-1은 `git mv`를 지시하나 이 폴더는 git 저장소가 아니었다. 다음 순서로 이미 처리했다.

```
git init
git commit -m "원본 두 시뮬레이션 보존 (rename 전 상태)"
git config core.autocrlf false  +  .gitattributes: "* -text"
git mv "image source waveguides" image-source
git mv "line waveguides"         line-wire
```

- **`core.autocrlf` 차단이 §1-1의 일부다.** 켜져 있으면 체크아웃 때 git이 원본의 줄바꿈을 CRLF로 바꾼다. 이것도 "원본 수정"이다.
- 이 저장소는 **독립 저장소다.** 기존 `waveguide_a`와 무관하며 **원격을 연결하지 않는다.**
- 작업 중 언제든 `git status`로 `image-source/`·`line-wire/` 아래가 깨끗한지 확인한다. 이것이 §1-1의 기계 검증 수단이다.
- 부모 폴더 `03-task(waveguide unified)`는 **바꾸지 않는다.** 모든 `<script src>`가 상대경로라 부모 이름이 URL에 들어가지 않는다. v1 §2-2의 `03-task/`는 표기상 축약으로 읽는다.

## 3. 모듈 구조 — 브라우저와 node에서 같은 코드

`verify.js`는 node에서 어댑터를 돌려야 하는데, 어댑터는 브라우저에서 `IMG`/`WIRE`/`WireWG`/`WGM` 전역에 의존한다. 어댑터 로직을 `verify.js`에 복사하면 §1-3의 정신을 깬다.

원본들이 이미 쓰는 UMD 패턴을 확장해, **각 파일이 스스로 자기 의존성을 해결**한다.

```js
// unified/adapters.js
(function (global, factory) {
  if (typeof module !== 'undefined' && module.exports) {
    var IMG = Object.assign({},
      require('../image-source/hankel.js'),  require('../image-source/images.js'),
      require('../image-source/physics.js'), require('../image-source/field.js'));
    var WIRE = Object.assign({},
      require('../line-wire/hankel.js'), require('../line-wire/field.js'));
    module.exports = factory(require('./geometry.js'), require('./measure.js'),
      IMG, WIRE, require('../line-wire/core.js'),
      require('../line-wire/higher-order/modes.js'));
  } else {
    global.Adapters = factory(global.GEO, global.Measure,
      global.IMG, global.WIRE, global.WireWG, global.WGM);
  }
})(globalThis, function (GEO, Measure, IMG, WIRE, WireWG, WGM) {
  /* imageScene, wireScene */
});
```

| 파일 | 의존성 | 브라우저 | node |
|---|---|---|---|
| `geometry.js` | 없음 | `global.GEO` | `module.exports = GEO` |
| `measure.js` | GEO | `global.Measure` | `require('./geometry.js')` |
| `adapters.js` | GEO, Measure, 엔진 4종 | 위 전역들 | 위 require 블록 |
| `render-unified.js`, `ui.js` | — | 브라우저 전용 | (require 안 함) |

- 브라우저에서 **추가 초기화 호출이 없다.** v1 §3의 `<script>` 순서가 만든 전역을 그대로 받는다. **더블클릭으로 열린다.**
- node에서는 `require('./adapters.js')` 한 줄. `core.js`는 `require.main !== module`이라 selfTest가 조용하다.
- ES 모듈·`fetch`를 쓰지 않는다.

### 3-1. `file://` 고유 출처 — ES 모듈이 금지인 실제 이유

`file://`은 **문서 하나하나가 고유한(opaque) 출처**다. 같은 파일이라도 자기 자신과 출처가 다르다. 따라서

| 방식 | `file://` 더블클릭 | 비고 |
|---|---|---|
| `<script src>` 클래식 | ✅ 동작 | 출처 검사 대상이 아님. 상위 폴더(`../`)도 됨 |
| `<link href>` | ✅ 동작 | 동일 |
| `<script type="module">` | ❌ 실패 | CORS 검사를 받음 |
| `fetch` / `XHR` | ❌ 실패 | 동일 |

`line-wire/higher-order/index.html`이 `../core.js`·`../hankel.js`·`../field.js`를 상위 폴더에서 불러와 정상 동작하는 것이 실증이다. 통합 페이지의 `../image-source/hankel.js` 로드도 같은 종류다.

> **참고 — 콘솔 메시지**
> `Unsafe attempt to load URL file:///… from frame with URL file:///… 'file:' URLs are treated as unique security origins.`
> 이 메시지는 **이 프로젝트 코드에서 나오지 않는다.** 두 원본 페이지의 JS·HTML 전체에 `fetch`·`XHR`·`iframe`·`<img>`·`<a>`·`window.open`·`location.*`·`import()`가 0건이다. 브라우저 확장의 콘텐츠 스크립트가 원인이며 동작에 영향이 없다. 시크릿 창(확장 꺼짐)에서 사라지는 것으로 확인할 수 있다.

## 4. `geometry.js` (v1 §4 그대로 + 3개 추가)

v1 §4의 `GEO` 객체를 그대로 쓰고 다음만 더한다.

```js
GEO.srcZ    = function () { return this.z0; };          // = 36 (셀, 관 입구 기준)
GEO.KAPPA_WIN = 'B';        // κ 창 기본값. 단계 6에서 확정 후 이 한 줄만 고친다.
GEO.nWires  = function (d) { return Math.round(this.L / d) + 1; };
GEO.wallXToPix = function (d) { return this.xLeft + (this.nWires(d) - 1) * d; };
```

`GEO.KAPPA_WIN`은 **앱(탭 1·2·3·4)이 쓰는 창**이다. `verify.js`는 이 값을 무시하고 A·B·C를 전부 돈다.

### 4-1. `walls.xToPix` 변경 근거 (v1 §5 수정)

`core.js:buildWires`는 `nW = round(L/d) + 1`개 위치에 도선을 놓으므로 마지막 도선이 `(nW−1)·d`에 있다.

| λ | d | `round(L/d)` | nW | 마지막 도선 z | L 초과 |
|---|---|---|---|---|---|
| 144 | 7.920 | 38 | 39 | 300.96 | ✓ |
| 90 | 4.950 | 61 | 62 | 301.95 | ✓ |
| 48 | 2.640 | 114 | 115 | 300.96 | ✓ |
| 33 | 1.815 | 165 | 166 | 299.475 | — |

**네 프리셋 중 셋이 L=300을 넘는다.** §8에서 도선관의 관 끝 경계선을 **보이게** 그리기로 했으므로 그 선이 실제 도선 끝에 있어야 한다.

**측정 창(`0.2L`, `0.7L`, `0.9L` 등)은 L=300 기준을 그대로 유지한다.** 여기만 바꾼다.

## 5. Scene 계약 (v1 §5 골격 유지)

세 번째 `method`를 만들지 않는다. **모드합은 `imageScene({modeInfinity:true})`** 이며 `method:'image'`를 유지한다.

```js
{
  method: 'image' | 'wire',
  Nx, Ny, y0pix, a, lambda, k, y0OverA,
  inc, scat, tot,                       // { re, im, Nx, Ny }
  walls: { yTopPix, yBotPix, xFromPix, xToPix },
  markers: [ { xPix, yPix, kind, weight } ],
  quality: { … }                        // method별로 다름
}
```

| method | `walls.xFromPix` | `walls.xToPix` | `quality` |
|---|---|---|---|
| `image` | 0 | `GEO.Nx` | `{ N, plateAvg, modeInfinity }` |
| `wire` | `GEO.xLeft` | `GEO.wallXToPix(d)` | `{ d, aw, awOverD, nW, lastWireZ, wallT }` |

검증 3열은 이렇게 만든다.

| 열 | 호출 | `resolvable`용 `d` |
|---|---|---|
| 모드합 | `imageScene({…, modeInfinity: true})` | 1셀 |
| 영상법 | `imageScene({…, N: 80})` | 1셀 |
| 도선관 | `wireScene({…, d: dAuto})` | `dAuto` |

### 5-1. 모드합의 산란장은 뺄셈 찌꺼기다 — 보정하지 말 것

`modeInfinity`에서 `scat = tot − inc`인데 `computeModeField`는 벽 사이(`jBot…jTop`)만 채운다. 따라서 **벽 바깥에서 `scat = −inc`** 가 된다. 산란장이 아니다.

§8에서 영상법 벽 바깥을 불투명 마스크로 가리므로 화면에 나오지 않는다. **의도된 동작이며 보정하지 않는다.**

## 6. `measure.js` — 측정 코드 한 벌 (v1 §7 + 창 3종)

§1-3을 지키려면 창 3종이 **함수 분기가 아니라 데이터**여야 한다.

### 6-1. κ 창 3종

```js
var KAPPA_WINDOWS = {
  // A — line-wire 원본 (core.js:kappaFitWindow ≡ modes.js:kappaWindowN)
  A: function (kThy) {
       var zStart = 0.15 * GEO.L;
       return { zStart: zStart, zEnd: Math.min(0.7 * GEO.L, zStart + 2.5 / kThy) };
     },
  // B — v1 §7-3
  B: function (kThy) {
       var zStart = clamp(GEO.z0 + 2 / kThy, 0.2 * GEO.L, 0.5 * GEO.L);
       return { zStart: zStart, zEnd: Math.min(0.7 * GEO.L, zStart + 2.5 / kThy) };
     },
  // C — image-source 원본 (main.js:computeFitInterval), 고정 길이 50셀
  C: function (kThy) {
       var zStart = GEO.srcZ() + 20;
       return { zStart: zStart, zEnd: zStart + 50 };
     }
};
```

- 창 함수는 **`{zStart, zEnd}`만** 돌려준다.
- `valid`(`zEnd > zStart` ∧ `isFinite(κ)` ∧ `κ > 0`), `resolvable`(`1/κ ≥ d`), v1 §7-4의 가드 4종은 **창 밖에서 세 창에 동일하게 적용**한다.

### 6-2. 반환 형식 (v1 §7-4 수정)

`null` 대신 사유를 함께 돌려준다.

```js
{ value: 0.0291, reason: null }
{ value: null,  reason: '분해능 한계 (1/κ < d)' }
```

| 사유 문자열 | 발동 조건 | 적용 |
|---|---|---|
| `창 무효` | `valid === false` | κ, k_z |
| `분해능 한계 (1/κ < d)` | `1/κ < d` | κ |
| `수치 바닥` | 끝 진폭 ≤ 0 | κ |
| `진폭비 부족 (< 1.5)` | 시작/끝 진폭비 < 1.5 | κ |
| `기울기 비물리 (≥ 0)` | 로그 기울기 ≥ 0 | κ |
| `창보다 λ_g가 김` | `λ_g > zEnd − zStart` | k_z |

G2 표, 탭 4 (A) 표가 **같은 문자열을 쓴다.** 추정값으로 채우지 않는다.

### 6-3. k_z (v1 §7-5 그대로 + 리플 절단은 진단 전용)

창은 `fitWindowZ(GEO.z0, GEO.L, κ_min)` **하나만** 쓴다. §7-5의 `λ_g ≤ zEnd − zStart` 조건을 신규 구현한다 (원본 두 코드에 없음).

리플 절단(§7-4 아래)은 **`verify.js` 진단 전용**이며 앱의 측정 경로에는 들어가지 않는다. v1 §7-6의 "포락선·기하평균 같은 별도 장치를 넣지 말 것"은 그대로 유효하다 — 절단은 같은 데이터에 창 끝만 바꾸는 것이지 새 장치가 아니다.

### 6-4. 모드 계수 (v1 §7-1 그대로)

`render.js:modeCoefficient`와 `modes.js:modeCoefGridN`이 수식까지 동일함을 확인했다. 하나로 합친다.

투영은 `j = jBot…jTop`(span+1점), 가중치 `sin(nπ(j−jBot)/span)`으로 **양 끝점이 0인 DST-I 형태라 이산 직교성이 정확히 성립한다.** 모드 간 누설이 없다. 이것이 모드합 열이 대조군으로 성립하는 근거다.

### 7-1. G2 — κ

조건: **a=60, λ=144 (λ/a=2.4), y₀/a=0.5, N=80, d=dAuto=7.920**

표 상단에 다음을 **그대로** 출력한다.

```
  이 열은 창의 우열을 가리지 않습니다. 측정 코드 정상 여부만 확인합니다.
```

각 표 머리에 열별 품질 지표를 붙인다.

```
모드합: (해석해)   영상법: N=80, plateAvg=____   도선관: d=7.920, wallT=____, aw=0.8
```

모드별 블록:

```
[G2] κ 측정/이론 (%)   a=60, λ=144, y₀/a=0.5
mode 1  (이론 κ = 0.0289431 /셀,  1/κ = 34.55셀,  resolvable ✓)
  창          z구간           모드합     영상법 N=80   도선관 d=7.920
  A 0.15L     [ 45.0, 131.4]  ---.-%     ---.-%        ---.-%
  B z0+2/κ    [105.1, 191.4]  ---.-%     ---.-%        ---.-%
  C 소스+20   [ 56.0, 106.0]  ---.-%     ---.-%        ---.-%
mode 2 …
mode 3 …
```

- `z구간`은 창과 κ 이론값에만 의존하므로 **행에 한 번만** 찍는다.
- 측정 불가 칸은 % 대신 §6-2의 사유 문자열.
- 모드 2·3도 같은 형식.

**중단 조건:** 모드합 열이 100.0%에서 **0.5% 이상** 벗어나면 측정 코드 버그다. 즉시 보고하고 중단한다.

> **이 중단 조건은 G2 3×3 표에만 적용된다.** 창 A(45.0)·B(105.1)·C(56.0)는 전부 소스 z=36을 지나 시작하므로 모드합이 정확히 100.0%여야 한다.
> **G2-PROFILE에는 적용하지 않는다** — §7-2 참조.

표 아래 한 줄로 대비를 정리한다 — 모드합이 100.0%인데 영상법·도선관이 측정 불가면, 그것은 **측정의 한계가 아니라 그 방법 자체의 한계**다.

### 7-2. G2-PROFILE — 국소 기울기 프로파일 (신규)

창 후보 3종은 추측 3종이다. 셋 다 나쁘면 넷째를 또 추측하게 된다. 대신 z를 따라가며 짧은 구간마다 κ를 재서 나열하면 **평탄 구간이 데이터에서 직접 읽힌다.**

```
부분창 길이 = max(20, 2/κ_이론) 셀
시작점 z    = 5 부터 step 15 셀, (0.9L − 길이) 까지
각 점에서 §7-4 가드 없이 로그 기울기만 계산   ← 가드는 여기서 끈다
```

| 모드 | κ_이론 | 부분창 길이 | 시작 z 범위 |
|---|---|---|---|
| 1 | 0.0289431 | 69셀 | 5 … 201 |
| 2 | 0.0951965 | 21셀 | 5 … 249 |

모드 1·2만 출력한다.

```
[G2-PROFILE] mode 1  부분창 69셀
  z중심   모드합   영상법   도선관     (A창 45.0~131.4, B 105.1~191.4, C 56.0~106.0)
   39.5    15.0%   ---.-%   ---.-%   ← 창이 소스를 가로지름
   54.5    71.9%   ---.-%   ---.-%   ← 창이 소스를 가로지름
   69.5    99.8%   ---.-%   ---.-%   ← 창이 소스를 가로지름
   84.5   100.0%   ---.-%   ---.-%
   ...
```

각 창의 구간을 표 옆에 표시해, 프로파일의 어느 부분을 그 창이 덮는지 눈으로 대조한다.
**앞쪽이 휘면 소스 근접장, 뒤쪽이 휘면 누설 바닥이다.**

> **이 프로파일이 창 결정의 1차 근거이고, A/B/C 3×3 표는 후보 검증이다.**

#### 7-2-1. 앞쪽에서 모드합이 100.0%가 아닌 것은 정상이며, 그것이 이 표의 두 번째 쓸모다

소스가 z=36인데 프로파일은 z=5부터 시작하므로 **앞쪽 부분창이 소스를 가로지른다.** 모드합의 `|c₁| = A·exp(−κ|z−36|)`이라 창 안에서 진폭이 올라갔다 내려오고, 로그 직선맞춤은 이렇게 나온다.

| 부분창 | 중심 z | 기울기 / κ_이론 |
|---|---|---|
| [ 5,  74] | 39.5 | **15.0 %** |
| [20,  89] | 54.5 | **71.9 %** |
| [35, 104] | 69.5 | **99.8 %** |
| (z ≥ 36 전체) | — | **100.0 %** |

(마지막 행은 경계를 보이기 위한 것으로, 실제 표본은 step 15의 5·20·35·50…이다.)

**그러니 프로파일 시작점을 옮기지 않는다.** 모드합이 100.0%에서 벗어나는 지점이 곧 *"이 창은 소스를 가로질러 기하학적으로 무효"* 라는 표식이 되어, **무효 구간의 경계를 추측이 아니라 데이터로 알려준다.**

- **§7-1의 0.5% 이탈 중단 조건은 여기에 적용하지 않는다.**
- **모드합이 100.0%가 아닌 행은 나머지 두 열도 무효다.** 표에서 그 행을 시각적으로 구분한다 — 행 끝에 `← 창이 소스를 가로지름`.

### 7-3. G3 — k_z

조건 (a)(b)(c)는 v1 §8 그대로이며, §9의 프리셋 ②③④와 같다. 창은 `fitWindowZ` 하나. 열은 G2와 같은 3종.

**리플 절단 진단** — 각 조건·각 전파 모드에서 k_z를 두 번 잰다.

```
(i)  표준   fitWindowZ 그대로
(ii) 절단   같은 zStart, zEnd → zStart + floor((zEnd−zStart)/(λ_g/2)) × (λ_g/2)
```

- `λ_g`는 **이론값**을 쓰고, **모드마다 자기 λ_g로 따로** 계산한다.
- 근거: 위상 섭동항 `arg(1 + ρ·e^{−2i k_z z})`의 주기가 정확히 `λ_g/2`이므로, 정수 주기로 절단하면 최소제곱 기울기에서 상쇄된다. v1 §7-6은 "여러 주기에 걸쳐 맞추면 상쇄된다"고 했으나 이는 **주기 수가 많을 때만** 참이다.
- 표에 **리플 주기 수**도 함께 찍는다.

| 조건 | 창 길이 | λ_g(모드1) | 리플 주기 수 |
|---|---|---|---|
| (a) λ=90 | 148.38 | 136.07 | **2.18** ← 가장 취약 |
| (b) λ=48 | 150.00 | 52.37 | 5.73 |
| (c) λ=33 | 150.00 | 34.32 | 8.74 |

두 값이 크게 다르면 리플 편향이 실재한다는 뜻이고, 같으면 무시해도 된다.

### 7-4. G3-AW — a_w 민감도 스캔 (신규)

조건 (b)(c)에서 `a_w ∈ {0.8, 0.5, 0.3}`으로 각각 측정한다. MoM 3회 추가라 비용이 없다.

## 8. `render-unified.js` — 마스킹 (v1 §9-3 전면 대체)

### 8-1. 영역이 세 종류이고 처리도 셋 다 다르다

| 행 | 영상법 | 도선관 |
|---|---|---|
| 1 입사파 | **마스크 없음** | **마스크 없음** |
| 2 산란파 | 벽 바깥 **불투명 마스크** | 마스크 없음 · **경계선만** |
| 3 전체장 | 벽 바깥 **불투명 마스크** | 마스크 없음 · **경계선만** |

**1행에 마스크가 없는 이유:** 입사파는 벽이 없는 자유공간 선원장이라 양쪽 모두 전 영역에서 정의되고, G1이 검증하는 대로 동일하다. **두 그림이 전 영역에서 똑같이 보이는 것이 G1의 시각판이다.** 한쪽만 가리면 "같은 입력에서 출발한다"는 메시지가 지워진다.

**2행 영상법 마스크는 필수다.** 영상원이 `y = y0 ± r·a`에 실제로 놓여 있어 벽 바깥에서 H₀가 발산하고, 행 스케일이 벽 사이 기준이라 그대로 두면 바깥이 통째로 포화된다.

### 8-2. 가리는 것과 선을 긋는 것을 구분한다

- **영상법 벽 바깥 = 가림.** `rgba(20,24,40,0.72)` 불투명 덮개 + 중앙에 `계산 영역 밖`. 원본 `render.js:drawExternalMask` 방식 그대로.
- **도선관 = 가리지 않음.** 벽 위치에 실선, 관 끝(`z=0`, `z=lastWireZ`)에 세로 점선을 긋고 바깥 영역에 라벨만 붙인다.

> 값을 **지우는 것**과 **구분하는 것**은 다르다.
> 영상법 바깥은 값 자체가 없어야 할 자리이고, 도선관 바깥은 값이 있으나 좌우 비교 대상이 아닐 뿐이다.

### 8-3. 캡션 (문구 그대로)

**영상법 패널**
```
영상 합은 벽 사이에서만 해를 재현합니다. 무한히 뻗은 도체판 바깥의 참값은 0이지만,
유한 개의 영상 합은 그 0을 만들지 못합니다. 그래서 이 영역은 표시하지 않습니다.
```

**도선관 · 벽 바깥**
```
도선 사이 틈으로 새어 나온 실재하는 장입니다. 이상적 도체판을 가정한 영상법에는
대응물이 없어, 좌우 비교 대상이 아닙니다.
```

**도선관 · 관 앞뒤**
```
도선 벽이 없는 자유공간입니다. 영상법은 이 위치에도 벽이 있으므로(무한 평행판),
같은 자리라도 좌우 비교 대상이 아닙니다.
```

> v1은 관 앞뒤에 대해 "영상법에는 대응하는 영역이 없습니다"라고 썼으나 **틀렸다.** 영상법의 도체판은 화면 전체 `x=0~520`에 걸쳐 있으므로 `z=−60` 같은 위치에도 벽이 있고 유효한 도파관 장이 존재한다. 대응물이 없는 게 아니라 **같은 자리에 서로 다른 기하가 있는 것**이다.

### 8-4. 바뀌지 않는 것

- **§9-2 행별 스케일 기준은 그대로 비교 영역(벽 사이) 내 최댓값이다.** 도선관 바깥이 보이게 되어도 기준을 바꾸지 않는다. `d = 0.055λ`에서 누설은 작아 포화되지 않을 것으로 예상하나, **실제로 포화되면 보고하고 중단한다 — 기준을 임의로 바꾸지 않는다.**
- §9-1 색 매핑(감마 기본 0.4), §9-4 눈금자 오버레이, §9-5 캔버스 규격은 v1 그대로.
- §5-1 마커 구분(영상원 = 속 빈 원 / 도선 = 채운 원 / 소스 = 노란 채운 원)은 v1 그대로. **미적 선택이 아니라 물리적 정직성 요구사항이다.**

## 9. UI 확정 사항 (v1 §10 보완)

### 9-1. 프리셋이 `a`도 설정한다

λ 범위가 24~150셀(두 원본의 교집합)이므로 비율만 적용하면 대부분의 `a`에서 벗어난다. 네 프리셋이 전부 성립하는 `a`는 4.4~6.2 cm뿐인데 슬라이더는 4.8~16.0 cm다.

**프리셋이 `a = 6.0 cm`(60셀)를 함께 설정한다.**

| 프리셋 라벨 | a | λ | y₀/a | 결과 | 검증 조건 |
|---|---|---|---|---|---|
| `① 완전차단  a=6.0 · λ=2.4a` | 6.0 cm | 144셀 (14.4 cm) | 0.500 | κ₁·L = 8.68 → 차단 무대 | **G2** |
| `② 단일모드  a=6.0 · λ=1.5a` | 6.0 cm | 90셀 (9.0 cm) | 0.500 | 모드 1만 전파 | **G3(a)** |

### 9-4. 분산 곡선 — 측정점 자동 삭제를 없앤다 (v1 §10-4 수정)

v1 §10-4는 *"점은 λ·a·y₀ 중 a나 y₀가 바뀌면 전부 지운다(곡선 자체가 달라지므로)"* 라고 했다. **근거가 틀렸다.** 정규화 축에서 곡선은 `a`에 무관하다.

```
가로축  u = λ/a
세로축  k_z/(π/a) = √( (2/u)² − n² )        ← u에만 의존
```

`k/k_c1 = (2π/λ)/(π/a) = 2a/λ = 2/u`이므로 `a`가 소거된다. **a=6 cm에서 잰 점과 a=10 cm에서 잰 점이 같은 자리에 놓인다.** `y₀`는 여기 세기(결합 `|sin(nπ·y₀/a)|`)만 바꾸고 분산 관계에는 들어가지 않는다.

게다가 §9-1로 프리셋이 `a`를 설정하게 되었으므로, 자동 삭제를 두면 **프리셋을 누를 때마다 점이 날아간다.**

**확정**

- 자동 삭제 **제거**. `[측정점 지우기]` 수동 버튼만 둔다.
- 각 점에 측정 조건 **`(a, λ/a, y₀/a, 방법)`을 툴팁**으로 붙인다.
- 누적 상한 200개(초과 시 오래된 것부터)는 v1 그대로.

> 서로 다른 `a`에서 잰 점들이 한 곡선에 모이는 것 자체가 **이 곡선이 `a`에 무관한 보편 관계임**을 보여준다. 탭 4가 하나를 더 말하게 된다.

### 11-6. 도선 격자의 유효 벽 위치 — 도선관 편차의 정체 (단계 5 발견)

도선 격자의 유효 반사면은 도선 중심선과 일치하지 않는다. 벽 하나당 변위는

```
δ = (d / 2π) · ln( d / (2π·a_w) ) ,      a_eff = a + 2δ
```

**자유 매개변수가 없다.** `d > 2π·a_w` → `δ>0` → 관이 넓어짐 → κ 감소.

G5 실측 대조 (a=60, λ=144, `a_w`=0.8 고정):

| d | δ | a_eff | 예측 κ비 | 실측 |
|---|---|---|---|---|
| 8.000 | +0.5917 | 61.183 | 93.52% | **93.5%** |
| 7.920 | +0.5731 | 61.146 | 93.73% | **93.7%** |
| 5.000 | −0.0042 | 59.992 | 100.05% | **100.1%** |
| 3.000 | −0.2464 | 59.507 | 102.68% | **102.7%** |

**4/4가 0.05%p 이내.** k_z도 같은 `a_eff`로 설명된다(③mode2 예측 98.4%/실측 98.5%, ④mode3 97.9%/97.9%).

> v1 §13이 검증에 쓴 `d=5`는 우연히 `d = 2π·a_w` = 5.027, 즉 **δ≈0 지점**이었다. 그래서 그 조건에서만 99.9~100.4%가 나왔다.

**정책 — 유효 벽 정합 `a_w = d/2π` (기본 켜짐)**

`a_w`는 물리 상수가 아니라 이산화 설계 변수이고 0.8도 임의의 선택이었다. 이 정합은 **자유 매개변수를 더하는 게 아니라 이미 있던 임의성을 물리적 기준으로 제거**한다. `d = 0.055λ`이므로

| | `a_w`=0.8 고정 | `a_w = d/2π` |
|---|---|---|
| δ | λ마다 −0.25 ~ +0.59 | **항상 0** |
| `a_w/d` | 0.101 ~ 0.606 (③④ 경고) | **0.1592 고정** |
| `k·a_w` | λ마다 다름 | **0.055 고정** |

얇은 도선 근사의 두 조건이 슬라이더 전 범위에서 동일하게 만족된다. 프리셋 ③④의 경고와 λ<2.91 cm 관통 문제가 원리적으로 사라진다.

**효과를 숨기지 않는다** — 체크박스로 끌 수 있고, `δ`와 `a_eff`를 항상 읽기값에 표시하며, `|δ| > 0.01`이면 탭 4에 `이론(a_eff)` 예측을 부가 표시한다. 자동 보정으로 가리지 않는다.

> 구현 주의: 자동일 때 `a_w`는 슬라이더 상한(2.0)에 구속되지 않는다. 수동 `d`=20이면 `a_w`=3.18.

**교차검증 — κ와 `wallT`는 독립 진단인데 둘 다 δ=0에서 최소다**

`wallT`(벽 누설 투과)는 별도 MoM으로 재는 완전히 다른 양인데, 정합 ON에서 `d`와 무관하게 0.0060~0.0094로 떨어진다(OFF에서는 0.0059~0.0558). **κ 정확도와 벽 밀폐도가 같은 지점에서 동시에 최적**이라는 것은 δ=0이 우연한 맞춤이 아니라는 강한 방증이다.

### 11-7. 영상법의 잘림 바닥과 Cesàro 총합 (단계 6a 조사, 6b 채택)

차단 영역의 영상 급수는 거친 교대급수라 유한 N 단순 합이 크게 흔들린다. **N을 올려도 낫지 않는다** — 창 C의 κ비가 N=80·160·320에서 101.9% → 78.9% → 106.4%로 진동한다(`plateAvg`는 단조 감소하는데도).

부분합의 산술평균(Cesàro)이 이를 해소한다. 항별 삼각 가중치로 등가 계산된다.

```
C_N = (1/N) Σ_{r=1..N} S_r = Σ_j t_j · (N − j + 1)/N
```

`addOneSource`가 `sign`을 곱셈 인자로 쓰므로 **원본을 고치지 않고** `sign`에 가중치를 실어 구현한다(`adapters.js`의 `imageScene({cesaro:true})`). 비용은 단순 합과 같다.

**정당성.** 영상 급수의 먼 항은

```
H₀(kr) ~ r^(−1/2) · e^{i(kr − π/4)}     에  (−1)^r 가 곱해진 형태
```

즉 **조건수렴형 진동 급수**다. 이런 격자합에서 Cesàro는 **수렴 급수라면 같은 극한을 주는 표준 총합법**이다. 답을 바꾸는 것이 아니라 도달 속도를 바꾼다. 실측이 이를 뒷받침한다 — Cesàro는 98.8 → 99.6 → 99.8%로 정확해를 향해 **단조 수렴**하고, 단순 합은 101.9 → 78.9 → 106.4%로 같은 목표를 **진동하며 통과**한다.

**단순 합의 진동은 결과이므로 보존한다.** 토글(`imageScene({cesaro:false})`)로 남기고 탭 4-C에 두 곡선을 겹쳐 그린다.

> `plateAvg`는 두 방식 모두 단조 감소하는데 κ는 단순 합에서만 진동한다. **경계조건 만족도가 좋아져도 관 내부 감쇠는 좋아지지 않는다**는 뜻이고, N=40이 우연한 골짜기가 아니라 **N축 전체가 진동**한다는 것을 보인다. 이것이 탭 4-C의 실제 내용이다.

### 11-8. 직선성 가드 R² (미확정)

Cesàro N=320에서 모드 3이 43.4%로 값을 내면서 §7-4 가드 넷을 **전부 통과**했다. 57% 틀린 값이다. `κ₃=0.1509`라 창 C 50셀에서 `exp(−7.54)=5.3e−4`까지 내려가 잘림 잔차 바닥에 잠긴 것이고, N을 올려도 바닥을 따라 기어오를 뿐이다(3.8 → 15.1 → 25.9 → 43.4%). **영상법의 실제 한계이므로 "측정 불가"로 나와야 한다.**

로그-선형 맞춤의 **결정계수 R²** 를 가드로 쓴다. 깨끗한 지수는 R²≈1, 바닥에 잠긴 잡음은 낮다 — **정답을 몰라도 판정 가능한 기준**이다. 사유 문자열은 `직선성 부족 (R²=○○)`.

실측 분포 (G2, 창 A·B·C 전부):

| 구분 | R² |
|---|---|
| 정상 측정 (κ·k_z 전부) | **0.9984 ~ 1.0000** |
| 모드 3 창 A 영상법 105.1% | 0.9998 |
| 모드 3 창 B 영상법 87.1% | **0.9514** |
| 모드 3 창 C 영상법 25.9% | **0.5910** |
| 모드 2 (결합 0, 잡음) | 0.0064 ~ 0.0892 |

**분리가 깨끗하다.** `R²_min = 0.99`면 정상 측정을 하나도 잃지 않고 87.1%·25.9%·잡음을 전부 걸러낸다.

> **확정: `R2_MIN = 0.99`** (단계 6b). 정상 0.9984~1.0000과 이상 0.5910~0.9514 **사이가 비어 있어** 안전하다. 가드 ON 후 모드 3 창 B·C가 `직선성 부족 (R²=0.951 / 0.591)`로 정확히 걸러진다.

**고차 차단 모드는 창 A에서만 측정된다** — 모드 3(κ₃=0.1509)에서

| 창 | 길이 | 결과 |
|---|---|---|
| **A** `0.15L` | `2.5/κ` = **16.6셀** (적응) | **105.1%, R²=0.9998** |
| B `z0+2/κ` | 16.6셀이나 시작이 뒤 | 직선성 부족 (0.951) |
| C `소스+20` | **50셀 고정** | 직선성 부족 (0.591) |

창 A는 길이가 `2.5/κ`로 **적응**해 κ가 클수록 짧아지므로 바닥에 닿지 않는다. 창 C는 50셀 고정이라 모드 3에서 `exp(−7.54)`까지 내려가 잠긴다. **이 데이터가 창 결정을 A로 뒤집었다** (§12-1).

**R²의 한계 — 계통 편향은 못 잡는다**

창 A 모드 3의 105.1%는 **R²=0.9998인데도 5% 벗어나 있다.** R²는 *"바닥에 잠겼는가"* 는 잡지만 *"기울기가 계통적으로 치우쳤는가"* 는 잡지 못한다. 잘 맞는 직선이 틀린 기울기를 가질 수 있기 때문이다.

**가드로서는 정상 동작이다.** 이 가드의 목적은 "무의미한 값 배제"이지 "정확도 보장"이 아니다. 탭 4는 값과 R²를 **함께** 표시하고, 오차 5% 초과 시 경고색으로 칠한다(v1 §10-4). 정확도는 게이트(§11-9)가 따로 본다.

### 11-5. 정수 λ/d 회피 (v1 §12-3) — 해당 없음

v1 §12-3의 `|d/λ − 정수| < 0.02` 규칙은 **Faraday 격자의 Floquet 합**에서 온 것이다. `d/λ`가 1 이상의 정수일 때 회절 차수 항이 누락되는 문제다.

**이 시뮬레이션은 Floquet를 쓰지 않는다.** `core.js:solveMoM`은 도선마다 미지수를 하나씩 두고 직접 푸는 MoM이라 주기성 가정 자체가 없다. 애초에 해당 없다.

정수 0 쪽은 규칙의 대상이 아니다. `d/λ → 0`은 **도선 벽이 연속 도체에 가까워지는 바람직한 극한**이며, 실제로 §7-6 G5의 수렴 스캔이 그쪽으로 조이는 방향이다.

> 참고: λ=150·수동 `d`=2면 `d/λ = 0.0133 < 0.02`로 산술적으로는 문턱에 닿는다. 문제가 없는 이유는 값이 문턱 밖이어서가 아니라 **규칙이 이 시뮬에 적용되지 않기 때문**이다.

### 12-1. 발견 기록 — `dAuto = 0.055λ` 완화 가능성 (채택하지 않음)

유효 벽 정합 ON이면 δ=0이 `d`와 무관하게 유지되므로(G5에서 d=3·5·8 전부 100.0%), 짧은 λ에서 `d`를 키워도 κ 정확도가 떨어지지 않는다. 벽 밀폐도도 유지된다.

| d | d/λ | 도선수 | wallT | MoM 비용 |
|---|---|---|---|---|
| 1.320 | 0.055 | 456 | 0.0027 | 94.8M |
| 2.400 | 0.100 | 252 | 0.0029 | 16.0M |
| 3.000 | 0.125 | 202 | 0.0033 | 8.2M |

`d=3.0`이면 MoM 비용이 **11배 감소**하는데 `wallT`는 거의 그대로다. 정합 도입 전이라면 δ가 커져 불가능했을 선택이다.

> **채택하지 않는다.** 논문 본문이 `d = 0.055λ`를 명시적으로 정당화하고 있어 시뮬 기본값을 바꾸면 논문과 어긋난다. 성능 문제가 실재하는지도 모르는 상태에서 물리 정책을 건드릴 일이 아니다. **논문 Methods를 개선할 재료로 기록만 해 둔다.**

**§12-5를 도입할 경우 — `resolvable` 판정이 등호에 걸린다**

절단은 창 길이를 `λ_g`의 정수배로 만들므로, §7-5의 `λ_g ≤ 길이` 조건이 **항상 정확히 등호**가 된다. 프리셋 ②로 계산하면:

```
창 [61.6235, 210]      길이 148.376548
λ_g = 136.067210        주기수 2.1809  → floor 2
절단 후 길이 = 2 × (λ_g/2) = 136.067210283 = λ_g       ← 차이가 정확히 0
```

두 곳에서 `λ_g`를 다른 경로로 계산하면 **부동소수점 때문에 판정이 뒤집힌다.**

```
절단을 도입하면 §7-5 resolvable 조건에 상대 허용오차를 넣거나
(λ_g ≤ 길이 × (1 + 1e-9)), 절단된 창은 resolvable 검사를 건너뛴다.
도입하지 않으면 해당 없다.
```

이 다섯 가지를 확정하기 전에는 **단계 7(렌더링)로 넘어가지 않는다.**
